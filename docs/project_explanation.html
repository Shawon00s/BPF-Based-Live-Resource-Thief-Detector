১ প্রজেক্টটি কী এবং কেন বানালাম?

BPF-Based Live Resource Thief Detector হলো একটি Real-time Security Monitoring System যেটি Linux কার্নেলের ভেতরে eBPF (Extended Berkeley Packet Filter) প্রযুক্তি ব্যবহার করে সিস্টেমের প্রতিটি process এর আচরণ পর্যবেক্ষণ করে এবং সন্দেহজনক কিছু ঘটলে তাৎক্ষণিক alert দেয়।

🎯 এক লাইনে প্রজেক্ট: "যেকোনো প্রসেস সিস্টেমের সম্পদ চুরি করছে কিনা (resource thief) — সেটা kernel level থেকে ধরে ফেলার একটি live detector।"

Linux এ প্রতিটি চলমান program কে Process বলে। প্রতিটি process এর একটি PCB (Process Control Block) থাকে যেখানে সব তথ্য রাখা হয়।

২.৪ Virtual Memory

প্রতিটি process মনে করে তার কাছে পুরো memory আছে — কিন্তু এটা illusion। Kernel Virtual Address Space maintain করে। eBPF data পড়তে আমরা bpf_probe_read_user_str() ব্যবহার করি কারণ user space pointer directly kernel থেকে access করা unsafe।

৩.১ BPF এর ইতিহাস

সালঘটনা

৩.২ eBPF Virtual Machine (VM)

eBPF হলো Linux কার্নেলের ভেতরে একটা mini computer। এর নিজস্ব:

  • 11টি 64-bit register (r0–r10) — r10 হলো stack pointer (read-only)
  • নিজস্ব Instruction Set — load, store, jump, call, arithmetic
  • 512 bytes stack — শুধু, বেশি না
  • Helper Functions — kernel এর সাথে কথা বলার নিরাপদ রাস্তা
চিত্র ৩: eBPF কোড compile থেকে kernel এ run হওয়া পর্যন্ত পুরো flow

৩.৩ eBPF Verifier — Safety Guard

⚠️ Verifier কেন দরকার? eBPF code kernel এর ভেতরে run হয়। একটা ভুল code পুরো OS কে crash করতে পারে। তাই kernel নিজেই code টা load করার আগে verify করে।

Verifier যা check করে:

  • Termination guarantee — কোনো infinite loop নেই (BPF program কে শেষ হতেই হবে)
  • Memory bounds — array/map access কখনো out-of-bounds না
  • Null pointer check — map lookup এর পর null check বাধ্যতামূলক
  • Stack limit — 512 bytes এর বেশি stack use করা যাবে না
  • Helper validation — শুধু approved kernel helpers ডাকা যাবে
/* Verifier কেন এই code reject করবে: */
u64 *count = read_count.lookup(&pid);
(*count)++;  // ERROR! count হয়তো NULL, check করতে হবে

/* Correct — Verifier এটা accept করবে: */
u64 *count = read_count.lookup_or_try_init(&pid, &zero);
if (count) {        // null check বাধ্যতামূলক
    (*count)++;
}

৩.৪ JIT Compilation

Verifier pass করলে eBPF bytecode কে JIT (Just-In-Time) Compiler x86_64 native machine code এ convert করে। এর ফলে eBPF প্রায় native C code এর সমান speed এ চলে।

৩.৬ eBPF Maps — Kernel ↔ User Space Communication (IPC)

eBPF Maps হলো এই প্রজেক্টের সবচেয়ে গুরুত্বপূর্ণ concept। এটা হলো shared memory যেটা kernel space ও user space দুদিক থেকে access করা যায়। এটাই আমাদের IPC (Inter-Process Communication) mechanism।

৬.১ ebpf_sensor.c — Kernel Space Sensor

এই ফাইলটা কার্নেলের ভেতরে চলে। BCC runtime এ এটা compile করে।

Data Structures — কী ডেটা পাঠাবো?

// ফাইল event এর জন্য structure
struct file_event_t {
    u32 pid;              // কোন process?
    u32 uid;              // কোন user এর process?
    char comm[TASK_COMM_LEN];  // process এর নাম (max 16 char)
    char filename[256];   // কোন ফাইল?
};

Maps — IPC Channel

// Ring buffer: kernel → user space event streaming
BPF_PERF_OUTPUT(file_events);    // file open events
BPF_PERF_OUTPUT(proc_events);   // process spawn events

// Hash map: pid → কতবার file read করলো
BPF_HASH(read_count, u32, u64);

Tracepoint Hook — কীভাবে syscall ধরি?

TRACEPOINT_PROBE(syscalls, sys_enter_openat) {
    struct file_event_t event = {};

    // PID পাওয়া: upper 32 bit = PID, lower 32 = TID
    event.pid = bpf_get_current_pid_tgid() >> 32;
    event.uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;

    // Process name — task_struct.comm থেকে পড়া
    bpf_get_current_comm(&event.comm, sizeof(event.comm));

    // User space pointer safely পড়া (বিপজ্জনক! তাই probe_read_user_str)
    bpf_probe_read_user_str(&event.filename,
                            sizeof(event.filename),
                            args->filename);

    // Counter বাড়াও (atomic, lock-free)
    u64 zero = 0;
    u64 *count = read_count.lookup_or_try_init(&event.pid, &zero);
    if (count) (*count)++;  // verifier requires null check!

    // User space এ পাঠাও (perf ring buffer দিয়ে)
    file_events.perf_submit(args, &event, sizeof(event));
    return 0;
}
💡 কেন bpf_probe_read_user_str? User space pointer কে kernel space থেকে সরাসরি dereference করা unsafe — page fault হতে পারে। এই helper function টা safely পড়ে এবং error handle করে।

Detection Logic — "Thief" চেনার নিয়ম

def handle_file_event(cpu, data, size):
    event = bpf["file_events"].event(data)   # ctypes struct
    pid   = event.pid
    comm  = event.comm.decode("utf-8").strip()
    fname = event.filename.decode("utf-8").strip()

    # ১. Whitelist check — known good processes skip
    if comm in WHITELIST_PROCESSES:
        return

    # ২. Rate window reset প্রতি WINDOW_SECONDS এ
    if time.time() - last_reset >= WINDOW_SECONDS:
        file_counts.clear()

    file_counts[pid] += 1

    # ৩. Sensitive file detection
    if is_sensitive(fname):
        log_event("ALERT", pid, comm, f"Sensitive file: {fname}")

    # ৪. Rate-based detection
    if file_counts[pid] > FILE_READ_THRESHOLD:
        log_event("ALERT", pid, comm, "Exfiltration suspected")

SSE — Server-Sent Events

@app.route("/stream")
def stream():
    """Browser এটা open রাখে — server push করে data"""
    def event_generator():
        while True:
            ev = event_queue.get(timeout=15)  # block করে অপেক্ষা
            yield f"data: {json.dumps(ev)}\n\n"  # SSE format!
            # timeout হলে heartbeat পাঠাও

    return Response(event_generator(),
                    mimetype="text/event-stream")  # special MIME type
📡 SSE vs WebSocket: SSE হলো one-way (server→browser) এবং HTTP এর উপর চলে — WebSocket এর মতো আলাদা protocol লাগে না। আমাদের case এ browser থেকে server এ কিছু পাঠাতে হয় না, তাই SSE perfect।

#প্রশ্নউত্তর
1 eBPF কী এবং traditional kernel module থেকে কীভাবে আলাদা? eBPF হলো kernel এর built-in VM যেখানে Verifier দ্বারা verified safe code চলে। Kernel module directly kernel code, একটা bug এ পুরো OS crash। eBPF তে crash সম্ভব না — worst case program load হয় না।
2 Kernel Space ও User Space কী? কেন divide করা? CPU এর hardware protection ring ব্যবহার করে memory ও privilege separate রাখা। User program ভুল করলে শুধু সে মরে, পুরো OS না। Security ও stability দুটোই নিশ্চিত হয়।
3 System Call কী? openat call হলে কী হয়? User space থেকে kernel service নেওয়ার mechanism। CPU syscall instruction execute করে — mode switch হয় Ring 3 → Ring 0, kernel handler চলে, ফলাফল return হয়, আবার Ring 3 এ ফেরে।
4 eBPF Verifier কেন দরকার? eBPF code kernel এ চলে। Verifier নিশ্চিত করে: (1) infinite loop নেই, (2) out-of-bounds memory access নেই, (3) null pointer dereference নেই। Safety guarantee ছাড়া kernel এ কোনো external code চালানো unsafe।
5 IPC কী? এই প্রজেক্টে কোন IPC ব্যবহার করা হয়েছে? Inter-Process Communication। Kernel ও User space এর মধ্যে eBPF Maps (বিশেষত BPF_PERF_OUTPUT ring buffer) ব্যবহার করা হয়েছে — এটা shared memory based IPC।
6 Race condition কী? এই প্রজেক্টে কোথায় সমস্যা হতে পারে? একাধিক thread বা CPU core একই data একসাথে modify করলে। file_counts dictionary multithreaded context এ race condition prone। eBPF map counter atomic, তাই kernel side safe। Python side এ lock যোগ করলে আরো robust হবে।
7 False Positive কী? এই detector এ কীভাবে কমানো যায়? Legitimate process কে malicious বলে চিহ্নিত করা। Whitelist বাড়ানো, threshold টিউন করা, ML-based baseline শেখানো দিয়ে false positive কমানো যায়।
8 SSE ও WebSocket এর পার্থক্য কী? SSE: one-way (server→client), HTTP এর উপর, automatic reconnect। WebSocket: bidirectional, আলাদা protocol, manual reconnect। আমাদের case এ browser শুধু receive করে তাই SSE যথেষ্ট।
9 JIT compilation eBPF performance এ কী ভূমিকা রাখে? eBPF bytecode কে x86_64 native machine code এ convert করে — interpreted execution এর চেয়ে ১০-১০০x দ্রুত। Production system এ JIT always enabled।
10 এই প্রজেক্টের limitation কী? (1) Root privilege দরকার। (2) eBPF 512 byte stack limit। (3) Threshold-based detection — sophisticated malware ধীরে ধীরে চুরি করলে ধরা যাবে না। (4) Python GIL performance bottleneck হতে পারে।
